# 03.5 Verification And Employee Review Gate

Date: 2026-06-10

This file defines the review gate for future implementation of the `03.n` patch guides.

## Static Verification

Always run after any modularization implementation:

```text
git diff --check
npm run typecheck
npx --yes madge --circular --extensions ts,tsx src --exclude 'src/bundle|src/react/view/excel/x-spreadsheet|resource'
```

## Focused Test Matrix

| Area | Required command |
|---|---|
| DOCX split | `npm run test:docx-editor-provider` |
| HWP limit guard | `npm run test:hwp-viewer-mode` and `npm run verify:hwp` |
| PPTX component split | `npm run test:pptx-phase4` |
| Markdown CommonJS boundary | `npm run test:markdown` |
| Cross-format regression | `npm run test:ci` |
| Bundle/regression | `npm run build` |

## Structural Assertions To Preserve

- No circular dependencies.
- No internal barrel file under `src/react/view/word/`.
- `Word.tsx` under 350 lines after the DOCX split.
- New DOCX helper files under 400 lines.
- `HwpEditorProvider.ts` and `createSecureRhwpEditor.ts` stay at or below the project-local 500-line maximum, with follow-up split work required because they are already over the canonical 400-line dev threshold.
- `Pptx.tsx` stays below the project-local 500-line maximum, with follow-up split work required because it is already over the canonical 400-line dev threshold.
- Provider-side files do not import React.
- React WebView helper files do not import VS Code extension-host APIs.
- DOCX save behavior assertions are moved to combined DOCX source checks, not weakened.

## Employee Review Instructions

Use two read-only employees after implementation:

### Backend / Architecture

Check:

- module boundaries,
- circular dependency output,
- provider/WebView dependency direction,
- HWP and PPTX line-count guard,
- CommonJS containment.

### Frontend / Docs

Check:

- DOCX component split keeps UI behavior equivalent,
- tests still assert behavior instead of only filenames,
- devlog and structure docs remain accurate,
- no visual/user-facing behavior was claimed without runtime evidence.

## PASS Criteria

Future implementation can be called ready only when:

- local verification commands pass,
- both employees return PASS or PASS-with-nonblocking-notes,
- any nonblocking notes are recorded in devlog,
- working tree is clean after commit,
- no push is performed unless the user explicitly asks in the same turn.
